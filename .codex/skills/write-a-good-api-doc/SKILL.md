# Agent 接口联调文档生成规范

## 1. 目的

当用户要求整理、生成或更新前后端联调接口文档时，Agent 输出一份面向接口使用方的简洁 Markdown 接口契约。只保留对方完成接入所需的当前生效事实：接口是什么、何时调用、怎么请求、参数怎么校验、返回什么、错误怎么处理，以及必要的兼容性或迁移要求。

交付文档是最终契约，不是分析报告、变更日志或工作记录。不得保留检索、核对、讨论、取舍、修订、推理、来源对比、原方案与现方案演变、候选方案、修改原因或其他调整过程的描述。

Agent 不默认以前端或后端为主。前端实现、后端实现、需求材料和旧文档都可以作为来源。

来源仅用于 Agent 内部核对事实。成品不得出现任一端的文件名、文件路径、类名、函数名、代码片段、代码行号、框架结构或其他实现定位信息，也不写“来源于前端/后端某文件”等过程说明。

## 2. 参考文件

- 生成文档时使用 `references/api-doc-template.md`。
- 需要设计判断时读取 `references/guideline-digest.md`。
- 不强制生成 OpenAPI。

## 3. 来源

可使用这些来源：

- 前端：调用封装、页面字段、表单校验、Mock、TypeScript 类型、请求示例。
- 后端：路由、Controller、DTO、Schema、Validator、响应类型、错误码。
- 需求：PRD、任务描述、字段说明、交互说明。
- 旧文档：Markdown、Apifox、OpenAPI、Postman、历史接口说明。

处理规则：

- 只有需求时，生成草案，缺失且影响接入的内容写 `待确认`。
- 已有实现时，按实现提取契约，但不在成品中记录文件或代码来源。
- 多来源冲突时，不自动定稿，列入待确认。
- 不确定的字段不要编造。

## 4. 工作流

1. 用 `rg` 搜索路由、调用点、类型、校验器、Mock、接口名、path、需求关键词和历史文档。
2. 标记变更类型：`新增`、`更新`、`废弃` 或 `待确认`。交付文档中不得同时保留对应的英文标签。
3. 提取 method、path、auth、content-type、参数、响应、错误码，并核对调用时机、前置条件、调用顺序、重试或轮询约定。
4. 参数按 `path`、`query`、`header`、`cookie`、`body` 标明位置。
5. 每个参数至少写字段、位置、类型、必填、约束、示例、说明。
6. 更新接口必须说明兼容性影响和调用方迁移点。
7. 使用模板生成 Markdown，必须保留“调用时机”和“错误示例”两个部分；仅在缺失项会影响接入时保留“待确认”。
8. 交付前执行最终事实筛选：删除所有实现证据、定位信息和调整过程描述，只保留当前生效且已核实的契约，以及影响接入的必要待确认项。
9. 检查文档阅读对象是否能仅凭成品完成接入；删除与调用方无关的背景、内部决策、实现说明和过程性反馈。
10. 生成文件时使用能直接体现接口或模块主题的中文文件名；交付前检查文件名是否清晰，禁止使用纯英文、拼音、缩写、无意义编号或泛化名称。

## 5. 输出要求

- 文档要短，避免堆空表和无用占位。
- 输出文件名必须为含义清晰的中文，直接体现接口或模块主题；不得使用纯英文、拼音、缩写、无意义编号或泛化名称（如 `api-doc.md`、`接口文档.md`），并保留 `.md` 扩展名。
- 只输出文档阅读对象完成接入所关注的内容：用途、调用时机、请求、参数、响应、错误、兼容性/迁移要求和必要待确认项。
- 交付内容只描述当前最终状态；不得出现“经过调整”“原方案”“现改为”“之前/之后”“为了……修改”等过程性描述，也不得写来源、检索路径、实现定位、推理过程或候选方案。
- 路由优先资源化表达；项目已有风格优先。
- body 字段用点路径表达嵌套字段，例如 `user.name`。
- 每份文档必须显式提供“调用时机”，至少说明触发场景、调用前置条件、调用顺序或依赖；涉及定时调用、重试或轮询时还要说明频率和停止条件。无法核实且影响接入时写 `待确认`，不得自行推断或描述核对过程。
- 错误响应至少包含状态码、业务码、触发条件、调用方处理。
- 每份文档必须显式提供“错误示例”代码块，示例应使用已核实的 HTTP 状态、业务码和响应结构；不同错误响应结构分别给出示例。无法核实的字段保留 `待确认` 并在“待确认”列出，不得编造、用过程描述替代或省略错误示例。
- 完成反馈包含文档路径、变更类型和待确认项；来源只在工作过程内部使用，不写入文档。
